## 1. ワークフローの必須キーは5つ

```json
{ "op": "add_workflow",
  "workflow": {
    "id": "notify_on_new_task",
    "name": "作業が登録されたら履歴に残す",
    "trigger": { "type": "on_create", "table": "task" },
    "actions": [ { "action": "create_record", "table": "task_log", "values": { "task": "$record._id" } } ],
    "history_table": "workflow_history"
  } }
```

- **必須**: `id` / `name` / `trigger` / `actions` / `history_table`
- **任意**: `act_as`(**この6つで全部**。7つ目のキーは書けない)
- **`history_table` は自動では作られない。** `add_table` で先に作っておくこと。

## 2. `trigger` —— 4種と、種別ごとに変わる必須キー

`type` は**必ず必要**で、値は `on_create` / `on_update` / `schedule` / `manual` の**4つだけ**。

| `type` | ほかに必須 | **書けない**キー |
|---|---|---|
| `on_create` | `table` | `at`, `older_than` |
| `on_update` | `table` | `at`, `older_than` |
| `manual` | `table` | `at`, `older_than` |
| `schedule` | `at`(`{ "hour": …, "minute": … }`。**両方必須**) | `older_than` は `table` を書いたときだけ書ける |

**`schedule` で `table` を書かないと、`$record.<フィールドID>` も `when` も1つも書けない。**

## 3. `actions` —— 5種と、種別ごとに変わる必須キー

`action` は**必ず必要**で、値は次の5つだけ。

| `action` | ほかに必須 |
|---|---|
| `create_record` | `table`, `values` |
| `update_record` | `table`, `values`, `target` |
| `call_external` | `connection`, `destination`, `payload` |
| `ai_transform` | `capability`, `prompt`, `input`, `output_field`, `fallback` |
| `run_function` | `function` |

**`when` はどの種別にも任意で書ける。** ただし形は1つだけである(下)。
アクションに書けるキーの全量は
[`reference/action-required-keys.md`](reference/action-required-keys.md) にある。

## 4. 値の形(取り違えが多いところ)

| キー | 形 |
|---|---|
| `values` | **オブジェクト**。キーはフィールドID、値はリテラルか `$record.<フィールドID>` の文字列。配列ではない |
| `target` | **3形だけ**: `$record._id` / `$record.<reference 型フィールドID>` / UUID のリテラル。多段の `$record.a.b` は書けない |
| `when` | `{ "field": "...", "equals": ... }` の**1形だけ**。`field` と `equals` の**両方が必須**で、それ以外のキーは書けない |
| `at` | `{ "hour": 9, "minute": 0 }`。**両方必須** |
| `act_as` | `$record.<参照フィールドID>` の**1形だけ**。ユーザ ID を直接書けない |

**`when` に比較(`gt` / `lt` / `gte` / `lte`)・`and` / `or` / `not`・`else`・入れ子・計算式を
書く場所は1つも無い。** 2つの条件を組み合わせたいときは、
**「`trigger` で行を絞る」×「`when` でアクションを絞る」の2層に分ける。**

**同じ名前の別のキーがある。混ぜないこと** —— **役割の規則(`app.roles[].rules`)にも `when` があり、
そちらは `and` / `or` / `not` を8段まで組める**(葉は「項目の値が定数と等しい」と
「項目の値が要求している人と等しい」の2形)。**それは誰に見せる / 書かせるかを行ごとに決める条件であって、
アクションを飛ばす条件ではない。****ワークフローの `when` は今日も等値1形のままである**(→ 役割の規則は
view-shape の説明書)。
**【2026-08-12 訂正(`V8-M32`。`V8-M26` / ユーザ決定 `D-V8-70`)。直前の括弧の中を1バイトも消していない】**
**「2形」は今日は偽で、あちらの葉は3形ある** —— **3つ目は `{ "field": "<項目ID>", "is_empty": true }`(その項目が空)である。**
**`is_empty` に書けるのも `true` だけ**(「空でない」は `not` で書く)。
**こちら(ワークフローの `when`)が等値1形だけであることは今日も変わらない。**

**【2026-08-16 追記(`V8-M47`)。上の表の `act_as` の行を1バイトも書き換えていない】**
**`act_as` は「誰として書くか」の名乗りであって、通行証ではない。** 満たすべき条件を足しておく。

- **書かなかったときの既定** —— **きっかけになった行の持ち主として書く**
  (手で起動したときは、押した人として書く)。
- **書いたとき** —— **その参照を1ホップだけ辿った先の行の持ち主として書く。** **2ホップは辿らない。**
- **辿れないときは名乗りが空になり、書き込みは通らない**(閉じる側に倒れる)——
  参照が空 / 参照先の行が無い / 参照先に持ち主が入っていない / 行が1つも無い時刻起動、の4つである。
- **書き先の表がアクセス権の宣言も持ち主の項目も持たないなら、判定そのものが起きない** ——
  **権限を1つも持たない相手の自動処理でも、今日どおり書ける。**
- **時刻起動(`schedule`)は今日も判定を1バイトも受けない** ——
  **権限の無い相手の行としてでも書ける。**

**【禁止】これを「`act_as` を書けば必ず通る」と書かない。**

**【2026-09-07 訂正。上の追記は1文字も消していない】**
**上の「**の4つである**」と「**判定そのものが起きない**」は、今日は不完全である** ——
**ボタンから起こす自動処理(`trigger.type` が `manual`)で `act_as` を書いたときだけ、関門が1つ増えた。**

- **その参照が指す行を、ボタンを押した人自身が読めなければ、その発火は失敗する。**
  **辿れていても失敗する** —— 上の4つに続く**5つ目**である。
- **失敗したときは1行も書かない**(途中まで書いて止まることはない)。**履歴には失敗が1行残る。**
- **書き先の表がアクセス権の宣言も持ち主の項目も持たなくても、この関門は起きる** ——
  **見るのは書き先ではなく `act_as` が指す行だからである。**
  **したがって上の「判定そのものが起きない」は、ボタン起動で `act_as` を書いたときには今日は偽である。**
- **行の作成・更新をきっかけに動く自動処理(`on_create` / `on_update`)と、決まった時刻に動く処理(`schedule`)には
  掛かっていない** —— **そちらでは今日も、押した人が読めない行の持ち主としても書ける。**

**【禁止】これを「なりすましを止めた」と読まない** ——
**止まるのは「押した人から見えない相手へのなりすまし」だけである。**

## 5. 関数(コードの島)の必須キーは5つ

```json
{ "op": "add_function",
  "function": {
    "id": "count_open_tasks",
    "name": "未完了の件数を数える",
    "code": "function run(input) { return { fields: [ { state: 'open', n: input.rows.length } ] }; }",
    "input": { "source": "table", "table": "task" },
    "output": { "fields": [ { "id": "state", "type": "text" }, { "id": "n", "type": "number" } ] }
  } }
```

- **必須**: `id` / `name` / `code` / `input` / `output`
- **任意**: `capabilities`(**この6つで全部**)
- `input.source` は `table` / `view` / `record` の**3つだけ**。
  `source: "table"` → `table` が必須 / `source: "view"` → `view` が必須
- `output` は **`fields` か `ops` のどちらか一方**。**両方書く形も、どちらも書かない形も拒否される。**
  `fields` の各要素は `id` と `type` が必須で、`type` はフィールド型9種のどれか。
- **島は `run_function` アクションからだけ呼べる。** 差分操作として実行することはできない。

## 6. できないこと(語彙の正からの逐語)

> 【できないこと・具体例】次のような要求は、言い換えても実現できません。

> **ただし「一定時間経ったか」だけは別で、これを『比較ができる』と読まないでください** —— 決まった時刻に発火するワークフロー(schedule)の trigger に対象の表を書くと、その表の行のうち「date 型の項目が N 日以上前」のものだけを対象にできます(trigger.older_than)。**これは時刻専用の1形であって、比較演算子が入ったわけではありません。** 2つの条件を組み合わせたいときも、述語を結合するのではなく「trigger で行を絞る」×「when でアクションを絞る」の2層に分けて書きます(and / or を書く場所はどこにもありません)。**しかも即座には走りません** —— 発火は毎日決まった時刻に1回だけなので、「3日ちょうど」ではなく「3日経ったあとの最初の発火時刻」に処理されます(cron 式・曜日・月・「5分ごと」の指定は今日もありません)。**1回の発火で処理できるのは 1000 行までで、超えるとその発火は1行も処理せずに打ち切られます**(打ち切られた行も、処理に失敗した行も、その日のうちには再試行されません)。

**外部への送信・受信・AI 呼び出し・失敗時の巻き戻し・集計とグラフについての
「できないこと」は [`reference/cannot-do.md`](reference/cannot-do.md) に置いてある。**
