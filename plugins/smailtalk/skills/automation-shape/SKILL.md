## 1. ワークフローの必須キーは5つ

```json
{ "op": "add_workflow",
  "workflow": {
    "id": "notify_on_new_task",
    "name": "作業が登録されたら履歴に残す",
    "trigger": { "type": "on_create", "table": "task" },
    "actions": [ { "action": "create_record", "table": "task_log", "values": { "task": "$record._id" } } ],
    "history_table": "workflow_history"
  } }
```

- **必須**: `id` / `name` / `trigger` / `actions` / `history_table`
- **任意**: `act_as`(**この6つで全部**。7つ目のキーは書けない)
- **`history_table` は自動では作られない。** `add_table` で先に作っておくこと。

## 2. `trigger` —— 4種と、種別ごとに変わる必須キー

`type` は**必ず必要**で、値は `on_create` / `on_update` / `schedule` / `manual` の**4つだけ**。

| `type` | ほかに必須 | **書けない**キー |
|---|---|---|
| `on_create` | `table` | `at`, `older_than` |
| `on_update` | `table` | `at`, `older_than` |
| `manual` | `table` | `at`, `older_than` |
| `schedule` | `at`(`{ "hour": …, "minute": … }`。**両方必須**) | `older_than` は `table` を書いたときだけ書ける |

**`schedule` で `table` を書かないと、`$record.<フィールドID>` も `when` も1つも書けない。**

**2026-09-30 に加わった。上の表の行は1バイトも書き換えていない。**
**`on_update` だけは、任意で `changed_fields`(項目 ID の配列)を書ける** ——
列挙した項目のどれかが「変わった」更新でだけ動く(定義は §4a)。
`on_create` / `manual` / `schedule` に書くと、差分は適用時に拒否される。
空の配列・同じ ID の重複・`_` で始まる ID・トリガー元の表に無い項目も拒否される。

## 3. `actions` —— 5種と、種別ごとに変わる必須キー

`action` は**必ず必要**で、値は次の5つだけ。

| `action` | ほかに必須 |
|---|---|
| `create_record` | `table`, `values` |
| `update_record` | `table`, `values`, `target` |
| `call_external` | `connection`, `destination`, `payload` |
| `ai_transform` | `capability`, `prompt`, `input`, `output_field`, `fallback` |
| `run_function` | `function` |

**`when` はどの種別にも任意で書ける。** ただし形は1つだけである(下)。
アクションに書けるキーの全量は
[`reference/action-required-keys.md`](reference/action-required-keys.md) にある。

## 4. 値の形(取り違えが多いところ)

| キー | 形 |
|---|---|
| `values` | **オブジェクト**。キーはフィールドID、値はリテラルか `$record.<フィールドID>` の文字列。配列ではない |
| `target` | **3形だけ**: `$record._id` / `$record.<reference 型フィールドID>` / UUID のリテラル。多段の `$record.a.b` は書けない |
| `when` | `{ "field": "...", "equals": ... }` の**1形だけ**。`field` と `equals` の**両方が必須**で、それ以外のキーは書けない |
| `at` | `{ "hour": 9, "minute": 0 }`。**両方必須** |
| `act_as` | `$record.<参照フィールドID>` の**1形だけ**。ユーザ ID を直接書けない |

**`when` に比較(`gt` / `lt` / `gte` / `lte`)・`and` / `or` / `not`・`else`・入れ子・計算式を
書く場所は1つも無い。** 2つの条件を組み合わせたいときは、
**「`trigger` で行を絞る」×「`when` でアクションを絞る」の2層に分ける。**

**同じ名前の別のキーがある。混ぜないこと** —— **役割の規則(`app.roles[].rules`)にも `when` があり、
そちらは `and` / `or` / `not` を8段まで組める**(葉は「項目の値が定数と等しい」と
「項目の値が要求している人と等しい」の2形)。**それは誰に見せる / 書かせるかを行ごとに決める条件であって、
アクションを飛ばす条件ではない。****ワークフローの `when` は今日も等値1形のままである**(→ 役割の規則は
view-shape の説明書)。

**`is_empty` に書けるのも `true` だけ**(「空でない」は `not` で書く)。

## 4a. 操作した人・更新前の値・今の時刻(`$actor` / `$previous` / `$now`)

**2026-09-30 に加わった。上の §4 の表の行は1バイトも書き換えていない。**
**§4 の表の「値はリテラルか `$record.<フィールドID>` の文字列」は今日は不完全である** ——
`create_record` / `update_record` の `values` の値には、`$record.<フィールドID>` と `$record._id` のほかに、
次の5つの参照を書ける。**どれも値の全体が参照1つのときだけ**である。

| 参照 | 入る値 | 書ける種別 |
|---|---|---|
| `$actor.id` | 操作した人の ID | どの `trigger` でも |
| `$actor.login` | 操作した人のログイン名 | どの `trigger` でも |
| `$actor.role` | 操作した人の**アカウントの役割1つ**(グループ経由の役割は入らない) | どの `trigger` でも |
| `$previous.<フィールドID>` | きっかけの行の**更新前の値**(未記入なら空) | **`on_update` だけ** |
| `$now` | 今の時刻(形は下) | どの `trigger` でも |

```json
{ "action": "create_record", "table": "verdict_log",
  "values": { "who": "$actor.id", "before": "$previous.verdict", "after": "$record.verdict", "at": "$now" } }
```

- **`$previous` を `on_create` / `schedule` / `manual` に書いた差分は、適用時に拒否される**(理由に `on_update` が名指しされる)。
  **トリガー元の表に無い項目を指した差分も拒否される**(書き込み先にだけ在る名前も同じ)。`_id` / `_updated_at` などの予約列は指せない。
- **`$now` の形は、書き込み先の項目の型で決まる** —— 書き込み先(トリガー元ではなく、そのアクションの `table`)の項目が
  `date` なら**アプリの時間帯の年月日**(例 `2026-09-30`)、それ以外なら**時差付きの秒まで**(例 `2026-09-30T10:23:45+09:00`)。
  時間帯はサーバの起動設定 `ST_TIMEZONE`(無ければ `Asia/Tokyo`)。**時刻まで残したいなら `text` の項目に書く。**
- **型の合わせ方は今日の規則のまま**(§4 の `values` と同じく、合わない差分は適用時に拒否される):
  - `$actor` の3つと `$now` は文字列なので、`text` / `date` / `select` の項目へ書ける。`number` / `boolean` の項目へは書けない。
  - **2026-09-30 訂正(直前の行を書き換えていない)**: `$actor` の3つを書ける項目は **`text` / `long_text` だけ**。
    `date` / `select` / `reference` / `image` / `file` の項目へ書く差分も、理由つきで適用時に拒否される(`$now` は今日どおり `date` の項目へ書ける)。
  - **2026-10-02 追記(上の行を書き換えていない)**: `$now` を `select` / `reference` / `file` の項目へ書く差分は、適用時には拒否されないが、実行のたびに値の検査で書込が断られる(きっかけの書込ごと戻る)。 **`$now` は `text` / `long_text` / `date` の項目に書く。**
  - `$previous.<項目>` はその項目の型を持つ。`number` の項目は `number` の項目へ、`boolean` の項目は `boolean` の項目へ書ける
    (`$previous.<number の項目>` を `text` の項目へ書くのは、`$record.<number の項目>` と同じく拒否される)。
  - `reference` の項目は、相手の行の ID のまま写る(表示名にはならない)。
- **書けないもの**: `$actor.email` のような4つ目の綴り・`$actor` だけ・`$previous._id`・`$today` など、上の5つの外の `$` で始まる形。
  固定の文字列とつなげる形・時刻の書式を選ぶ形・日付の足し引き。
  **`target` / `payload` / `input` / `fallback` / `act_as` にこの5つを書いた差分は拒否される**(参照として解かれるのは `values` の値だけ)。
- **項目 ID を付け替える差分は、`$record.<項目>` と同じく `$previous.<項目>` と `changed_fields` の項目名にも追随する。**
- **`when` の `equals` に `$` で始まる値(`$actor.id`・`$now`・`$record.<項目>` など)を書いても参照としては解かれず、その綴りの固定の文字列として比べる**
  (適用は通る)。操作した人や今の時刻で実行を分けることはできない。

### 入口ごとの `$actor`

| 入口 | `$actor` の値 | 更新者の欄(`st_updated_by`)に入る値 |
|---|---|---|
| 画面・HTTP(1行ずつ・まとめ書き) | ログイン中の人 | その人の ID |
| あなた(AI の口。MCP) | 起動設定 `ST_MCP_ACTOR` で名乗った人 | その人の ID |
| 画面のボタンから動かす手動の処理(`manual`) | **押した人**(`act_as` を書いていても押した人。`act_as` の相手ではない) | 押した人の ID |
| 連鎖(自動処理が起こした次の自動処理) | 起点の値をそのまま引き継ぐ | 起点と同じ |
| 関数(コードの島)の書込(`write_ops` / `write_back` / `output_table`) | 起点の値をそのまま引き継ぐ | 起点と同じ |
| 受信口 | `id` と `login` は空、`role` は `inbound` | 空文字 |
| 決まった時刻の処理(`schedule`) | `id` と `login` は空、`role` は `schedule` | 空文字 |
| AI に頼む処理(`ai_transform`)の書き戻し | **その処理が誰として動いているか**(`act_as` の先の持ち主か、きっかけの行の持ち主)。**起点の人と食い違うことがある** | 同じ人の ID |
| 会員登録・招待の承諾 | 登録した本人 | 本人の ID |
| 役割の変更 | 操作した人(役割を変えられた人ではない) | 操作した人の ID |
| 差分の適用に伴って名簿へ入る行 | 差分を適用した人 | 同じ人の ID |
| `undo` | 自動処理は動かない | 書き換わらない |

- **`$actor` は送られてきた内容から1バイトも読まない。** 画面や HTTP の本文に `$actor.id` の綴りや他人の ID を書いても入らない。
- **`act_as` は `$actor` を変えない** —— `act_as` が変えるのは「誰として書くか」の判定だけで、`$actor` は押した人・起点の人のまま。
- **AI に頼む処理の書き戻しは、起点の人と食い違う**(上の表)。揃える設定は無い。
- **【2026-10-02 訂正。直前の行を1バイトも消していない】act_as を書かず、きっかけの行に持ち主の列(st_owner)も無い表では、上の表の AI の行は誤り** —— 誰として動いているかが分からないので、$actor は空で、AI の書き戻しは更新者の欄を書き換えず、直前の値(最後に更新した人)のまま残す。変更の履歴の変えた人も空のまま。
- **【2026-10-02 追記。直前の行を1バイトも消していない】自動処理の履歴の表(`history_table`)に `st_updated_by` の項目を置いても、実行の履歴の行には何も押されず、空(null)のまま**(空文字ではない)。 また、AI に頼む処理の書き戻しの変更の履歴の入口は自動処理と出て、AI の書き戻しと見分ける値は無い。
- 利用者の表に行の無い ID(退会した人など)は、`login` と `role` が空になる。

### `changed_fields` の「変わった」

- 更新前の行と更新後の行を、列挙した項目ごとに比べる。**どれか1つでも変わっていれば動く。**
- 比べる前に、未記入・`null`・空文字を同じ「空」とみなす。**`boolean` の項目では「空」と `false` も同じとみなす。**
- `number` は数として比べ、それ以外は文字として比べる。**したがって日付の書き方の違い
  (`2026-09-30` と `2026-09-30T00:00:00Z`)は「変わった」とみなす。**
- **何も変えずに画面で保存しても動かない**(実行の履歴にも残らない)。
  自動処理が自分の表の、列挙していない項目を書き換えても動かない。
- **`changed_fields` を書かなければ、今日どおり更新のたびに動く。**

### 書き出したアプリ(独立して動かす版)での違い

書き出したアプリも、上の5つの形・`changed_fields`・島の入力 `actor` / `previous`・更新者の欄(`st_updated_by`)を同じように扱う。
**次の点だけが違う**(書き出したアプリには利用者の表もログインも無く、日付の項目を時刻つきの型で持つため)。

- **`$actor.id` は、書き出したアプリに差し込んだ名乗りの ID である**(差し込んでいなければ空)。
  **`$actor.login` と `$actor.role` はいつも空**(受信口の `role` は `inbound`、決まった時刻の処理の `role` は `schedule`)。島の入力 `actor` も同じ。
- **更新者の欄は表示名に差し替わらず、ID のまま返る。** 入力フォームにこの項目を挙げると入力欄が出る(送った値は捨てられ、ID が入る)。
- **`$now` の時刻はデータベースの時計で読む。** 時間帯は起動設定 `ST_TIMEZONE`(無ければ `Asia/Tokyo`)で決める。
  `date` の項目に書いた年月日は、その日の世界標準時の0時として入り、読み返すと時刻つきの綴りになる。
- **`changed_fields` で `date` の項目を比べるとき、同じ時刻の書き方の違い(`2026-09-30` と `2026-09-30T00:00:00Z`)は「変わっていない」とみなす**(上の本体の比べ方と逆になる)。
- **`$previous.<項目>` と島の入力 `previous` の日付の値は、世界標準時の時刻つきの綴りになる。**

## 5. 関数(コードの島)の必須キーは5つ

```json
{ "op": "add_function",
  "function": {
    "id": "count_open_tasks",
    "name": "未完了の件数を数える",
    "code": "function run(input) { return { fields: [ { state: 'open', n: input.rows.length } ] }; }",
    "input": { "source": "table", "table": "task" },
    "output": { "fields": [ { "id": "state", "type": "text" }, { "id": "n", "type": "number" } ] }
  } }
```

- **必須**: `id` / `name` / `code` / `input` / `output`
- **任意**: `capabilities`(**この6つで全部**)
- `input.source` は `table` / `view` / `record` / `actor` / `previous` の**5つだけ**。
  `source: "table"` → `table` が必須 / `source: "view"` → `view` が必須
  `actor`(操作した人)と `previous`(更新前の行)は `table` / `view` を書かない。
  **`previous` は `on_update` のワークフローから呼ぶ関数だけが持てる**(それ以外から呼ぶと適用時に拒否される)。
  **2026-09-30 追記**: `actor` の島が受け取るのは `$actor` と同じ `{ id, login, role }` の組(入口ごとの値は §4a の表)、
  `previous` の島が受け取るのは**きっかけの行の更新前の行全体**である。配列形の入力の中にも書ける。
- `output` は **`fields` か `ops` のどちらか一方**。**両方書く形も、どちらも書かない形も拒否される。**
  `fields` の各要素は `id` と `type` が必須で、`type` はフィールド型9種のどれか。
- **島は `run_function` アクションからだけ呼べる。** 差分操作として実行することはできない。
- **【2026-10-02 訂正。上の例を1バイトも消していない】上の `add_function` の例の `code` は、そのままでは動かない**(呼ぶと関数の実行の失敗になり、きっかけの書込ごと断られる)。 理由は3つ —— (1) 入口の関数の名前が `run` だと島が見つけられない(`export default function` か、名前を `main` にする)。 (2) `source: "table"` の入力は行の配列そのもので、`input.rows` は無い。 (3) `output` が `fields` の島が返すのは行の配列で、`{ fields: [ … ] }` ではない。 動く形は `"code": "export default function (input) { return [ { state: 'open', n: input.length } ]; }"` である。 **名簿の表の `on_create` に置いた自動処理は、利用者の登録と役割の付与の手続きの中でも動く**(名簿への自動登録を書いた名簿)。 そこで失敗するか関数が `reject` すると、登録と役割の付与が断られる。

## 5a. 関数から書込を断る(`reject`)

`input.source` が `record` の関数の例(`input` はきっかけの行の値):

```js

  if (input.score > 100) reject("100 を超える点数は入れられません");
  return [];
}
```

**【2026-10-02 追記。上の例を1バイトも消していない】上の例は、検査だけをして何も書かない島である。** 呼ぶときは関数の `output` を `{ "ops": true }` にし、ワークフローのアクションを `{ "action": "run_function", "function": "<関数のID>", "write_ops": true }` にする(`ops` の島が空の配列を返すと何も書かない)。 `output` を `fields` にして `output_table` で呼ぶと、返した行で出力先の表が全置換されるので、`[]` を返すたびにその表が0行になる。

- **第2引数の `{ reject }` が渡るのは、島の本文に `reject` という語(前後が英数字や `_` でない形)を書いたときだけである。**
  本文にその語が無い島の呼び出しは、今日と1バイトも変わらない(引数は1つのまま)。
  **第2引数を別の名前で受けて、名前を文字列で組み立てて取り出す形(`ctx["rej" + "ect"]` など)では渡らない** —— 本文に語が無いためである。
  `rejected` や `reject_x` のような、語の一部に含むだけの綴りも数えない。
- **文言は1〜200文字の文字列**(文字で数える)。空・201文字以上・文字列でない値を渡すと、汎用の失敗になり、文言は出ない。
- **呼んだ時点で断りが決まり、島はそこで止まる。** 例外を握りつぶしても、後で値を返しても、その後に時間切れ・メモリ超過・出力超過になっても断りのままで、2回呼んだときは1回目の文言である。
- **`reject` 以外の例外の本文は今日どおり捨てられる**(利用者にも履歴にも出ない)。業務の理由で断るときは、例外を投げずに `reject` を呼ぶこと。
- **起動のされ方ごとの違い**:
  - `on_create` / `on_update`: **きっかけの書込ごと、同じ器の中の書込が全部戻る**(連鎖の奥で呼んでも同じで、最初の文言が一番外の書込の応答にそのまま返る)。同じワークフローのそれより後のアクションは動かない。

  - `schedule`(決まった時刻): **`reject` は汎用の失敗になる。** 文言は残らず、書込も戻らず、後のアクションも今日どおり動く。
  - **【2026-10-02 訂正。直前の行を1バイトも消していない】** 直前の行は、時刻の処理から直接呼んだ関数のときだけ正しい。 時刻の処理のアクションが書いた行をきっかけに動いた自動処理の関数が `reject` を呼んだときは、その書込は戻り、時刻の処理の実行の履歴に、そのアクションの失敗として前置きと文言が残る(時刻の処理の後のアクションは止まらない)。
  - **【2026-10-02 追記】画面のボタンの処理の HTTP の口は、断られても今日どおり `200`** で、文言は応答の `failures` の要素に「アプリが定めた理由で断りました: 」の前置きつきで入る(`422` にはならない)。

- **入口ごとの返り方**: 画面は入力フォームの上に文言、HTTP は `422` と `kind: "app_rejected"`、

  **他人の行の値を文言に埋めると、断られた人にその値が漏れます。** プラットフォームは文言の中身を調べない。
