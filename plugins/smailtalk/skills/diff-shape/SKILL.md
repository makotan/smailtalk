## 1. 差分パッチの外側 —— 必ずこの3キー

```json
{
  "diff_id": "add-task-table",
  "intent": "作業の一覧を持てるようにする",
  "operations": [ { "op": "add_table", "table": { "…" : "…" } } ]
}
```

- `diff_id` / `intent` / `operations` の**3つとも必須**。1つでも欠けると差分全体が拒否される。
- `diff_id` は **59文字以内**(undo が `undo-<diff_id>` という名前を作るため)。
- `intent` は**空文字が不可**。
- `operations` は**1件以上の配列**。
- **この3つ以外のキーを外側に書けない。**

**【2026-08-25 追記】この3キーを検査するより前に、権限が見られる。**
**`apply_diff` も `dry_run_diff` も、順序は「名乗り → `app` × `write` の規則 → `intent`」である。**
**規則が無い相手には、`intent` を空にしていても `intent` の話は返らず、権限の断りが返る。**
**着手前は `dry_run_diff` だけが `intent` を先に見ていた** —— **その差は今日は無い。**
**役割の規則を1本も書いていないアプリでは、持ち主でも両方が断られる**
(直し方は `set_roles` で `owner` に `target: "app"` / `can: ["write"]` を書き戻すこと)。

## 3. 書けるキーは閉じている(`additionalProperties` が `false`)

1つの操作に書けるキーは
`op` / `table` / `field` / `view` / `changes` / `workflow` / `function` / `theme` / `roles` の**9つだけ**で、
**この9つの外側の名前を1つでも足すと差分全体が拒否される。**

**【2026-08-11 訂正(`V8-M29`。台帳 `T-G9a`)。旧文を1バイトも消していない】**
**旧文の逐語は「`op` / `table` / `field` / `view` / `changes` / `workflow` / `function` / `theme` / `user_kinds` / `roles` の**10つだけ**で、**この10つの外側の名前を1つでも足すと差分全体が拒否される。**」である。**
**`user_kinds` キーは廃止された。**

同じことがテーブル・フィールド・画面の定義にも当たる。**「近そうな名前」を作って書けない。**

| 定義 | 必須キー | 書けるキー(これで全部) |
|---|---|---|
| `table` | `id`, `name`, `fields` | 左の3つ + `representative_field`, `reference_search_fields`, `access_control` |
| `field` | `id`, `name`, `type` | 左の3つ + `required`, `options`, `reference_table`, `unique`, `unit`, `emphasis`, `hide_when_empty`, `reference_picker`, `reference_search_fields` |
| `view` | `id`, `type`, `table` | → view-shape の説明書 |
| `workflow` | `id`, `name`, `trigger`, `actions`, `history_table` | → automation-shape の説明書 |
| `function` | `id`, `name`, `code`, `input`, `output` | → automation-shape の説明書 |

**型ごとに増える必須キーが2つある**(書き忘れると拒否される):

- `type` が `select` のとき → `options` が必須
- `type` が `reference` のとき → `reference_table` が必須

**`reference` 型にだけ書ける任意キーが2つある**(名前だけでは意味が取れないので、ここに書く):

- **`reference_picker`** —— **この項目を画面でどう選ばせるか。** 値は `list`(一覧から選ぶ。既定)/
  `type_filter`(打った文字で候補を絞る)/ `search`(別の面を開いて探す)の**3つだけ**で、
  4つ目を書くと差分全体が拒否される。**書かなければ `list` と同じで、画面は1バイトも変わらない。**
  **どの器で描くか・候補の上限件数はプラットフォームが決めるので、1つも書けない。**
  **入力画面ごとに変えたいときは、画面の側の `reference_pickers` に書く**(→ view-shape の説明書)。
- **`reference_search_fields`** —— **候補を探すとき、打った文字を照合する列。**
  値は**フィールドIDの配列**だけで、**1本以上8本以下・同じ列を2度書けない。**
  **書けるのは実在する `text` / `long_text` だけ**で、**役割の規則(`app.roles[].rules`)が
  `target: "field"` で名指しした項目**を書くと差分全体が拒否される
  (**`V8-M20` 以前はここが「`audience` を宣言した項目」だった。そのキーは撤去された**)。
  **照合は部分一致を `or` で結んだ形に固定**で、演算子・条件式・ワイルドカードは1つも書けない。
  **同じ名前のキーが `table` の側にもある** —— そちらは「このテーブルが参照されたときの既定」で、
  項目の側に書けばその項目だけの上書きになる(**優先順位は 項目 > テーブル > 代表の項目1本**)。

## 3a. 複数人で共有する表に書く `access_control`(全量)

**表の定義の6キー目が `access_control` である**(上の表の右端に在る)。
**書かなかった表は今日と1バイトも変わらない** —— 書くかどうかは表ごとに選ぶ。
**`access_control` に書けるキーは7つで、8つ目は書けない。** **そのうち必須は4つである。**

| キー | 必須か | 形 |
|---|---|---|
| `enabled` | **必須** | 真偽値。`false` は「宣言していない表」と同じ扱いになる |
| `permissions` | **必須** | 配列(1件以上8件以下)。この表で使う権限名の全量 |
| `creator_permission` | **必須** | 文字列(`^[a-z0-9_]{1,32}$`)。行を作った人に自動で入る権限名 |
| `grant` | **必須** | 誰に何を許すかを記録する表と、その列の名指し |
| `members` | 任意 | このアプリの利用者を並べた表と、その列の名指し |
| `groups` | 任意 | まとまりを並べた表の名指し |
| `inherit_from` | 任意 | 付与を引き継ぐ元の表IDの配列。**2件まで**(0件でもよい) |

**`permissions` の1件は `id` / `name` / `read` / `write` / `delete` の5キーで、5キーとも必須である。**
`read` / `write` / `delete` は真偽値で、**書けるのは「できること」だけである。**
`id` の形は `^[a-z0-9_]{1,32}$` で、
**予約された4語(`owner` / `editor` / `viewer` / `anonymous`)は書けない** ——
役割の名前と同じ綴りを権限名に使わせないためである。
**`creator_permission` に書いた名前が `permissions[].id` に実在するかは、差分を適用するときに検査される。**

**`grant` は5キー**(`table` / `target` / `member` / `group` / `permission`)で、
**そのうち必須は3つ**(`table` / `target` / `permission`)である ——
`member` と `group` は、相手を人で指すか、まとまりで指すかによって使い分ける。
**`members` は3キー**(`table` / `account` / `group`)で、**そのうち必須は2つ**(`table` / `account`)。
**`groups` は1キー**(`table`)で、**それが必須である。**

**`access_control` を宣言した表は、名簿(`members` の `table`)に自分の行が無いと、
行を作る要求が 400 で断られる。** **名簿の `account` 列に書くのはログイン名ではなく利用者IDである。**
**最初の1行をどう入れるかは説明書 app-build に書いてある**(ここでは繰り返さない)。

**`inherit_from` は、今日どの説明書にも例が1つも無い。** 値は表IDの配列で、上限は2件である。

## 5. 値の形

- **ID(`diff_id` / `table.id` / `field.id` / `view.id` ほか)** は

## 5a. 真偽値の項目は、行を作るときに必ず値を書く

**あなた(MCP)や API が `boolean` の項目のキーを省いて行を作ると、その項目には
明示的に `null` が書かれる**(カーネルの逐語コメントは
「部分更新でない新規作成では、未指定は明示的に null を書く。」である)。

**絞り込みは素の `=` に落ちる** —— `boolean` 専用の分岐も `IS NULL` の分岐も1つも無い。
**したがって `null` の行は `equals` に `true` を書いても `false` を書いても当たらない。**

**ブラウザの入力画面から作った行では起きない** —— 画面の側が `boolean` だけを
`false` で初期化して送るからである。**起きるのは、キーを省いて行を作ったときである。**

**そこで、`boolean` の項目は行を作るときに必ず `true` か `false` を書くこと。**

**【正直に書く】この挙動を固定する検査は、`src` の下の `*.test.ts` を探した範囲では
見つけられなかった**(「1本も無い」とは書かない)。

## 6. できないこと(語彙の正からの逐語)

> 【できないこと・具体例】次のような要求は、言い換えても実現できません。

> 【できるが、元に戻せないこと】フィールドやテーブルの削除・リネーム・型変更は、remove_field / remove_table / change_table / change_field で実際に実行できます。できないのは、その結果を選んで元に戻すことです —— 消えた値の退避先はスナップショットだけで、それを戻す手段(undo と、その undo をやり直す redo)はいずれもデータベース全体を巻き戻します。undo はデータベース全体を巻き戻します(redo も直前の undo が戻した時点へ、やはりデータベース全体を巻き戻すだけで、消したフィールドの値だけを選んで戻せるわけではありません)。したがって、消したあとに入力されたレコードを保ったまま、消したフィールドの値だけを戻す手段はありません。「スナップショットがあるので戻せます」「あとで復元できます」とユーザに説明してはいけません。

**アプリごと消すことについての「できないこと」は
[`reference/cannot-do.md`](reference/cannot-do.md) に置いてある。**
