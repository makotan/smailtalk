**形は節1つ。** `type` は `stack`(縦に積む)/ `cluster`(横に並べて折り返す)/ `sidebar`(脇と本文)/ `switcher`(幅があれば横、無ければ縦)/ `grid`(格子)/ `split`(両端に振り分ける)の6種。

**同じ子を2回書く・画面に無い名前を書く・根を1段目として4段目の節を書く・項目のまとまり(`field_sections`)と両方書く、はどれも差分全体が拒否される。** 木に置かなかった表示項目は拒否されない。
**書くと画面に描かれる。** 木に置かなかった表示項目は木の後ろに今日の順で縦に積まれ、木に置いたボタン(`action:…`)は葉の位置に描かれて元の場所には描かれない。`switcher` / `sidebar` / `cluster` / `grid` は置かれた場所の幅が足りないと縦に積み直す・折り返す(画面幅の条件を書くのではない。断点は書けない)。

## 一覧に横スクロールせずに入る列の数(ブラウザで実測した)

**【2026-08-16 追記(`V8-M47`)。上の `preset_column_width` の行を1バイトも書き換えていない。**
**あの行は選択肢の名前しか書いていないので、実数と、それが何列に化けるかをここに足す】**

- **ルートの文字の大きさは 16px、シェルの最大幅は `60rem`(= 960px)である。**
- **列幅の選択肢の実数は `narrow` = `6rem`(96px)/ `standard` = `12rem`(192px)/
  `wide` = `24rem`(算術では 384px。**この1つだけは実測していない**)。**
- **一覧の器が実際に使える幅は 960px ではなく 720px である** —— 960px から、
  シェルの左右の余白と、画面一覧の脇の帯(`12rem`)と、その隙間(`1rem`)が引かれる。
- **ビューポートの幅が 1280px でも 1440px でも(ルートが 16px のとき)、`standard` の列は
  3列までが横スクロールせずに入る。4列目から溢れる。**
- **1024px 以上では、ビューポートをいくら広げても器は 720px のままで、答えは3列で変わらない。**
  **効くのは 1024px より狭いときだけである**(900px → 3列 / 768px → 2列 / 640px → 2列 / 375px → 1列)。
- **3列以下では `standard` は効かない** —— 表は幅を固定して描くので、
  指定した幅の合計が器に満たないと、余りが等分される(3列のとき1列 239.94px になった)。

**測り方**: 一覧の器(横スクロールする要素)の `clientWidth` を取り、
各列の見出しの右端がその器の右端を超えないものを数えた。
**境目は `scrollWidth > clientWidth` が3列で偽・4列で真に変わるところである。**

## `reference_pickers` の意味(名前だけでは取れないので書く)

**入力画面(`form`)ごとに、参照項目の選び方を上書きする。**

```json
"reference_pickers": { "partner": "search", "category": "type_filter" }
```

- **キーは参照項目のフィールドID、値は `list` / `type_filter` / `search` の3つだけ**
  (`list` = 一覧から選ぶ。既定 / `type_filter` = 打った文字で絞る / `search` = 別の面を開いて探す)。
  **4つ目を書くと差分全体が拒否される。**
- **`form` にだけ書ける。** `list_view` / `detail_view` に書くと差分全体が拒否される ——
  一覧と詳細は値を表示するだけで、選ぶ操作が構造的に無いためである。
- **優先順位は「画面 > 項目 > 既定」の1本だけ。** ここに書いた項目は、項目の側の
  `reference_picker` より優先される。書かなかった項目は項目の側に、それも無ければ既定に倒れる。
- **全置換である。** 項目ごとに1本ずつ足す / 消す手段は1つも無い。**前進では外せない。**
- **書かなかった画面は1ピクセルも変わらない。**
- **どの器で描くかは書けない。** 器の割り当てはプラットフォームが持つ。
- **何を打つと当たるかは、この画面の側では決められない** —— それは参照される側のテーブル、
  または参照する項目の `reference_search_fields` である(→ diff-shape の説明書)。

## 並べ替え・絞り込み・子一覧・操作の形

```json
"sort": { "field": "due_on", "order": "asc" }
"sort": [ { "field": "state", "order": "asc" }, { "field": "due_on", "order": "desc" } ]
```

`field` と `order` は**両方必須**。`order` の値は `asc` / `desc` の2つだけ。

```json
"filter": { "and": [ { "field": "state", "equals": "open" },
                     { "field": "due_on", "lte": "2026-12-31" } ] }
```

## 一続きの流れ(`flow`)の値と、段の並び

```json
{ "op": "add_view",
  "view": { "id": "entry_list", "type": "list_view", "table": "entry",
            "columns": ["title", "state"],
            "flow": { "id": "apply", "step": 1, "kind": "input" } } }
```

### 3つの鍵だけで、4つ目は無い

| 鍵 | 必須 | 値 | よくある取り違え |
|---|---|---|---|
| `id` | **必須** | 流れの名前(文字列) | **画面のIDではない。** 同じ流れに属する画面は、全部この同じ名前を書く |
| `step` | **必須** | **1から始まる整数** | 0・負の数・小数・文字列は書けない |
| `kind` | **必須** | `input` / `confirm` の2つだけ | 他の語(`review` / `done` など)は書けない |

**この3つ以外の鍵を1つでも書くと、差分全体が拒否される。**
**段の見出し・アイコン・色・所要時間・次の段の条件を書く場所は、語彙のどこにも無い。**

### どの種別に書けるか

| 種別 | `flow` を書けるか | `kind` に書ける値 |
|---|---|---|
| `list_view` | 書ける | **`input` だけ** |
| `form` | 書ける | **`input` だけ** |
| `detail_view` | 書ける | `input` / `confirm` |
| `report_view` | **書けない**(差分全体が拒否される) | ― |

### 差分を適用するときに拒否される形(実際のメッセージの要点)

| 書いた形 | どうなるか |
|---|---|
| 同じ `id` の中で同じ `step` を2つの画面が持つ | **拒否。**「流れ …… の中で、位置(step)…… が重複しています」 |
| 同じ `id` の中で `step` が飛んでいる(1,2,4) | **拒否。**「位置(step)が連番になっていません。…… が抜けています」 |
| `step` が 1 から始まっていない(2,3) | **拒否**(上と同じ理由。1 が抜けている扱い) |
| `report_view` に `flow` を書いた | **拒否**(その種別では書けないキー) |
| `form` / `list_view` に `kind: "confirm"` を書いた | **拒否** |
| `flow` に4つ目の鍵を書いた | **拒否** |

**別の流れであれば、同じ位置を書いてよい**(位置が衝突するのは同じ `id` の中だけである)。
**`id` そのものの重複は拒否されない** —— **同じ名前を複数の画面が持つのが、流れの作り方である。**

### 段の並びは宣言から導かれる

- **並び順を保存する場所は無い。** マニフェストのどこにも「流れの一覧」は無い。
- **「次」は、同じ `id` を持ち `step` がいまの位置 + 1 の画面1つである。**
- **その画面がそのアプリに居なければ、そこが最後の段として扱われる**(次へは進まない)。

### 後から変えられるか

**`update_view` の `changes` に `flow` を書けるので、後から差し替えられる。**
**ただしキーを消す手段は無い**(別の値に差し替えるか、`undo` で戻す)。
**差し替えた結果、位置が重複したり飛んだりする形になれば、その差分は拒否される。**

### 次の段へ進むきっかけと、運ばれるもの

**きっかけは画面の種別で違う**(表と条件は view-shape の説明書の「一続きの流れ」の節にある)。
要点だけをここにも置く:

- **入力画面は保存が成立したら次の段へ進む。**「次へ」のボタンは出ない。
- **一覧画面と、`kind` が `input` の詳細画面には「次へ」のボタンが出る。**
- **`kind` が `confirm` の詳細画面には「次へ」は出ない** ——
  **その画面に書いた値の書換のボタン(`actions` の `set` の形)の書込が成立したときに進む。**
- **自動処理を起こすボタン(`actions` の `run` の形)では、段を宣言していても進まない。**
- **「次へ」は、次の段の画面がその人に見えないときには出ない**(ボタンごと出ない)。
- **運ばれるのは、次の段が同じテーブルの詳細画面のときの、いま扱っている行1件だけである。**
  **それ以外では何も運ばれず、前の段で入力した値は1つも運ばれない。**
- **流れは1つのアプリの中に閉じる** —— **外部の URL も、別のアプリの画面も書けない。**
- **ボタンの文言は今日も宣言できない。**

| 「戻る」 | **`flow` を書いた `form` だけ**(`modal: true` を除く) | ボタン1つ | 押すと**履歴を1つ戻る** |

## 規則の条件(`when`)—— 行ごとに判定する

**表(`table`)と項目(`field`)を対象にした規則にだけ、`when` を1つ書ける。**
**画面(`view`)とボタン(`action`)には書けない**(スキーマが `when: false` で塞いでいる)。

```json
{ "target": "table", "table": "task", "can": ["read", "write"],
  "when": { "and": [ { "field": "state", "equals": "doing" },
                     { "field": "assignee", "equals_current_user": true } ] } }
```

- **葉は2形だけ**: `{ "field": ..., "equals": ... }`(値が定数と等しい。`equals` は文字列 /
  数値 / 真偽値)と `{ "field": ..., "equals_current_user": true }`(値が要求している人と等しい)。
  **`equals_current_user` に書けるのは `true` だけ**で、`false` は書けない。
  - **【`V8-M26` / ユーザ決定 `D-V8-70`。2026-08-11。直前の「葉は2形だけ」を1バイトも
    消していない】その字面は今日は偽で、葉は3形ある。** 3つ目は
    `{ "field": ..., "is_empty": true }`(**その項目が空**)。
    **空とみなすのは `null` と、値が入っていないことと、長さ0の文字列の3つだけで、
    `0` と `false` は空ではない。**
    **`is_empty` に書けるのも `true` だけ**で、`false`(空でない)は書けない —— 否定は `not` で書く。

    (`equals_current_user` はログインしていなければ必ず偽で、向きが違う)。

    ```json
    { "or": [ { "field": "st_owner", "equals_current_user": true },
              { "field": "st_owner", "is_empty": true } ] }
    ```

- **枝は3形だけ**: `{ "and": [...] }` / `{ "or": [...] }`(**どちらも2件以上**)/ `{ "not": {...} }`。
- **入れ子の深さの上限は8段**(絞り込み `filter` と同じ上限)。超えると差分全体が拒否される。
- **`field` はその規則が名指しした表の項目でなければならない** —— 実在しない項目を書くと
  差分全体が拒否される。**参照を1ホップも辿らない**ので、別の表の項目は書けない。
- **比較(`gt` / `lt` / `gte` / `lte`)・集計値・件数は1つも書けない。**

## ログインしていない人に表ごと見せる(`hidden_fields`)

**「ログインしていない人にも一覧を見せたい」と頼まれたら、この節の順で書く。**
**表そのものを未ログインに開く規則と、その表の画面を未ログインに開く規則は別である**(両方が要る)。

```json
{ "op": "set_roles",
  "roles": [
    { "id": "owner",  "name": "管理" },
    { "id": "editor", "name": "編集" },
    { "id": "viewer", "name": "閲覧" },
    { "id": "anonymous", "name": "ログインしていない人",
      "rules": [
        { "target": "table", "table": "item", "can": ["read"], "hidden_fields": ["cost", "staff_memo"] },
        { "target": "view", "view": "item_list", "can": ["read"] }
      ] }
  ] }
```

(`set_roles` は全置換なので、実際には既存の役割の規則もすべて書く。上は形だけを示す。)

### 何が読めるようになるか

- **`anonymous` に `{ "target": "table", "table": "<表ID>", "can": ["read"] }` を書いた表は、`st_public` が無くても、
  ログインしていない人がその表の行を読める**(一覧・1件・子一覧)。
  **条件(`when`)を書いたときは、条件に合う行だけ**が読め、合わない行の1件は「その行はありません」と同じ答えになる。
- **書き込み・削除は今日どおり 401 である**(未ログインに書く口は開かない)。**集計表(`report_view`)も未ログインには開かない。**
- **`st_public` を持つ表は今日のまま** —— 立てた行だけが読め、表に規則を書いても読める行は広がらない。
- 未ログインの読取には、公開指定の行を読むときと同じ回数の制限が掛かる。
- **読める行の `image` は未ログインにも配信される。`file` 型のファイルは1件も配信されない。**

### 未ログインにだけ隠す項目(`hidden_fields`)

```json
{ "target": "table", "table": "<表ID>", "can": ["read"], "hidden_fields": ["<項目ID>"] }
```

- **並べた項目は、ログインしていない人には値も項目名も渡らない。** 並べ替え・絞り込み・合計・区切りにも使えず、
  名指しした読取は存在しない項目を名指ししたときと同じ 400 になる。
- **ログインした人の見え方は1つも変わらない。** ログインした人から隠したいときは、今日どおり項目(`field`)の規則で書く。
- **書かなければ全項目が見える**(既定は「見える」)。
- **`hidden_fields` を書けるのは `anonymous` の表の規則だけ**である。ログインした人の役割・画面・項目・ボタンの規則に書くと
  スキーマで拒否される(拒否の場所に `hidden_fields` が載る)。
- **適用の時点で断られる形**:
  - 表に実在しない項目を並べる。
  - **隠した項目を消す(`remove_field`)ときは、同じ差分の `set_roles` で `hidden_fields` から外す**(外さずに消すと拒否される。
    同じIDで作り直したときに黙って隠れ直すのを防ぐため)。
  - **未ログインの規則の条件(`when`)に、隠した項目は使えない**(返る件数から値が推せるため)。
- **項目のIDを変えると、`hidden_fields` の中も追随する**(隠していた項目が改名で見えるようにはならない)。
- **追記(2026-10-02)**: **消せない印(`st_undeletable`)と直接作れない印(`st_no_direct_create`)の列は、`hidden_fields` に書かなくても、
  ログインしていない人の並べ替え・絞り込み・区切り・合計に自由には使えない。** 通るのは、開いた一覧画面の宣言と同じもの(検索の語を足した絞り込みを含む)と、
  未ログインに開いた詳細画面の子一覧(`related`)の宣言と同じ並べ替えだけ。 公開の画面に印の列で並べる・絞る宣言を書くのは今日どおり効くが、
  **その列を一覧の列に出すと、ログインしていない人が見出しを押して並べ替えたときに断られて一覧が出ない**(列に出さないほうがよい)。

### 読めない表と、守りを外す差分

- **次の表は、`anonymous` に表の規則を書いても未ログインには読めない(差分は通るが効かない。読むと 401)**:
  `st_owner` を持つ表 / `access_control` を宣言した表 / 付与・名簿・グループを記録する表 /
  どれかの役割の読取規則の条件に「自分」(`equals_current_user`)を書いた表 / `_` で始まるシステムの表。
- **守りを外す差分は、適用の前に拒否される** —— 未ログインに閉じていた表から、`st_owner` / `access_control` /
  付与・名簿・グループの宣言 / 条件の「自分」/ `st_public` を外す差分は、その表を読む `anonymous` の規則が残っていれば通らない。
  **先に(同じ差分の `set_roles` でもよい)`anonymous` の規則からその表を外す。**
  同じ差分で規則を外せば通るので、開くかどうかを人に確かめてから書くこと。

### 画面の変わり方

- **未ログインに開いた画面の参照の列は、参照先の表も未ログインで読めるときは名前で出る。**
  参照先の表が読めなければ、今日どおり「(見つかりません: 行ID)」と出る。
- 未ログインの表の規則で読める表では、その表の一覧画面を未ログインに開いていなくても、子一覧と参照の名前が出る
  (`st_public` の表では今日どおり、その形の画面を未ログインに開いていないと0件になる)。
- **アプリの入口 `/apps/<アプリID>` を未ログインで開くと、未ログインに開いた一覧画面のうち、
  画面の並び順で最初のものが出る。** その画面にはログインへの導線が出る。
- **訂正(2026-09-28。直前の行は消していない)**: 入口に出るのは、未ログインに開いた一覧画面のうちメニューに載せるもの(`menu_listed` を `false` にしていないもの)で、
  画面の並び順で最初のものである。 メニューに載せる一覧画面が1つも無いときだけ、載せない画面も含めて並び順で最初のものが出る。
  未ログインのメニューとログイン画面の画面の一覧にも、メニューに載せない画面は出ない(URL を直に開けば今日どおり開ける)。
- **ログイン画面は `/apps/<アプリID>/login` にある。** 未ログインに開いた一覧画面が1つも無いアプリは、今日どおり入口でログイン画面が出る。
  詳細画面だけを未ログインに開いたアプリも、入口ではログイン画面が出る。
- ログインした後の見え方は今日と同じである(`/login` の URL のままでもアプリの入口と同じ表示になる)。

### 限界(人に説明してから書く)

1. **後から足した項目は、足したときに `hidden_fields` へ書き足さなければ見える。** 項目を足す差分を書くたびに、
   未ログインに見せてよい項目かを確かめること。
2. **未ログインに見せる画面の絞り込み(`filter`)には、隠した項目を使わない。** 1つでも使うと、未ログインの画面では
   絞り込みごと外れ、表の規則で読める行がすべて並ぶ(画面の絞り込みは読める範囲を決める壁ではない)。
   並べ替え・合計・区切り・列に使った分は、その部分だけが外れる。
3. **参照先の表の代表の項目を隠すと、未ログインの画面の参照は名前ではなく「(見つかりません: 行ID)」と出る**(行は在る)。
4. **`file` 型の値(ファイルのID)は、隠さなければ行に載る**(ファイルそのものは配信されない)。
5. **未ログインで 200 かつ 0件は、「行が無い」と区別できない**(規則を書き忘れた表も空に見える)。
6. **書き出したアプリ(独立して動かす版)は、行を読む口だけが同じ答えを返す** —— ログイン画面・入口の画面・画像の配信・
   公開画面の定義の口は無い。未ログインの読取の回数の制限も無い。
7. **AI(MCP)の口には未ログインの経路が無い。** 未ログインで何が見えるかは、ブラウザでログインせずに開いて確かめてもらう。
