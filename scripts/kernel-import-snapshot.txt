# **ADR-0009 の限定に照らした審査の結論: 許される。** 理由は3点である。
#
# 1. **限定2 の条文が名指しで塞いでいるのは `normalizeSort` 系(整列規則の再実装)で
#    ある。**その趣旨は「**同じ規則が2箇所に実装され、静かに食い違うこと**」を防ぐこと
#    であり、ここで import しているのは規則ではなく**プロセスの入口の配線**である。
#    `recover` の2件が既に同じ位置取りで通っている(V1-M1-T04 §12)。
# 2. **`recover` と同じく「この配線を作ることがタスクの目的そのもの」である。**
#    ADR-0013 §6a が「**カーネルはアクティブなアプリのマニフェストを読んで発火を判定する**」
#    と定めた以上、**誰かがカーネルにその周期処理を始めさせなければならない。**
#    始められる場所はプロセスの入口(`src/server/index.ts`)しか実在しない。
# 3. **向きが逆になっていない。**`src/kernel/workflow-scheduler.ts` は `src/server/` を
#    1バイトも参照しない。**`src/server/app.ts` の `withAppDb` / `withStore` を export
#    する案を採らなかったのはこのためである**(判断3)—— export すると kernel が server の
#    ヘルパに依存し、層の向きが反転する。スケジューラは自前で DB を開閉している。
#    **`src/server/app.ts` は1バイトも変更していない。**
#
# **代わりに増やさなかったもの**: `runSchedulerTick` / `SCHEDULER_TICK_INTERVAL_MS` は
# 製品コードから1度も値 import していない(前者はテスト専用の観測口、後者は定数)。
# **層またぎは必要最小の2件に絞ってある。**
