# MCP 実地検証ハーネス (V0-P6-T03a)

本物の対話型 LLM(ヘッドレスの Claude Code)を会話クライアントとして MCP サーバを叩き、
**その証跡を機械的に判定できる形で残す**ための道具。CP-5 で一度きりの手順として実施したものを、
再実行可能な仕組みに固定してある。

- `run.ts` — シナリオを1本実行し、証跡を残す
- `judge.ts` — 保存された証跡を機械的に判定する(人間の主観を入れない)
- `scenarios/*.md` — 人間が打つプロンプトと、そのシナリオの隔離条件
- 出力先 — `docs/evidence/cp-6/transcripts/<連番>-<シナリオID>/`

---

## 前提条件

実行前に、次の4つを満たしていること。

### 1. `claude` CLI が存在する

```console
$ claude --version
2.1.214 (Claude Code)
```

PATH に無い場合は `ST_TRIAL_CLAUDE_BIN` で絶対パスを渡す。

```console
$ ST_TRIAL_CLAUDE_BIN=$HOME/.local/bin/claude mise exec -- bun run scripts/mcp-trial/run.ts --scenario bootstrap
```

### 2. Web サーバを起動しておく(必要。ただし run.ts は面倒を見ない)

MCP サーバと Web サーバは**別プロセス**である。`get_preview_url` は URL を返すだけで、
その URL が実際に見えるかは確認していない(ADR-0005 Consequences)。
**人間がブラウザで確認するターンがあるシナリオでは、事前に評価用のデータルートで Web サーバを立てておく。**

```console
$ ST_DATA_ROOT=data-bootstrap mise exec -- bun run server
smailtalk server: http://127.0.0.1:3000 (dataRoot=data-bootstrap, timeZone=Asia/Tokyo)
ブラウザで開くアドレス: http://localhost:3000 (127.0.0.1 でも画面は出ますが、そちらでは保存できません —— localhost で開いてください)
```

**人間が確認するターンでは、2行目のアドレス(`localhost`)で開くこと。** 1行目の `127.0.0.1` で開くと
画面は出るが保存だけが 403 で断られる(書き込みを許す出所の既定は `http://localhost:3000` /
`http://localhost:5173` の2本で、`127.0.0.1` はどちらとも一致しない)。
**既定と違うポートで起動したときは、その旨の警告が標準エラーに1行出る。**

**既定のデータルートはシナリオごとに分かれる**(`data-<シナリオID>`。§データルートはシナリオごとに分かれる)。
`--dry-run` は実行時の `ST_DATA_ROOT` を標準エラーに出すので、Web サーバに渡す値はそれを見れば分かる。

**`ST_DATA_ROOT` を Web サーバと MCP サーバで一致させること。** ここの不一致は
`docs/mcp-quickstart.md` が「最頻の混乱」と書いている事故そのものである。
`run.ts` は MCP 側の `ST_DATA_ROOT` を評価用の値に固定するが、Web サーバは別プロセスなので面倒を見られない。

### 3. ビルドは不要

解釈実行なので `build:web` もサーバ再起動も要らない(ADR-0003 §2)。
CP-5 ではブラウザのリロードだけで追加した列が現れることを確認している。

### 4. 評価用データルートを分離する(コードで強制済み)

既定は `data-<シナリオID>`。リポジトリの `data/` は `assertIsolatedDataRoot` が**拒否する**ので指定できない。
`data-` で始まらない名前も拒否する(`.gitignore` が `data-*` を除外しているため、
評価データが誤ってコミットされない)。

リポジトリにコミットされている `.mcp.json` は**変更しない**。`run.ts` は `ST_DATA_ROOT` だけを
差し替えた評価専用の設定を試行ディレクトリに書き出し、`--mcp-config` で渡す。

### 5. 名乗り(`ST_MCP_ACTOR`)に、アプリの設定を変える権限があること(**2026-08-25 追加**)

`V8-M31` 以降、アプリを名指しする道具は「名乗った利用者がそのアプリに登録されていること」を
要求する(`--actor` で渡す。既定の `.mcp.json` は空欄なので、共有アプリのシナリオでは必須)。

**`V10-M28` から、要求はもう1段ある。** `apply_diff` / `undo` / `redo` / `delete_app` /
`request_*` の8本に加えて、**`dry_run_diff` にも「アプリの設定を変更できる」
(役割の規則の `target: "app"` / `can: ["write"]`)が要る。**

- **`create_app` で作ったアプリなら、持ち主にこの規則が最初から2行入っている** ——
  **その持ち主を名乗る限り、既存のシナリオは着手前と1本も変わらずに走る。**
- **効くのは、`set_roles` でその規則を書き落としたアプリと、`roles` を持たない定義である。**
  **そのとき `dry_run_diff` は持ち主にも断られる。**
- **これは「破壊的変更の進め方」の5段(まず `dry_run_diff` → 同意 → `apply_diff` →
  検証 → 問題があれば `undo`)の**第1段**である。**
  **権限の無い名乗りで走らせると、シナリオは第1段から進めない** ——
  **その試行は「AI がドライランを飛ばした」ではなく「名乗りに権限が無かった」である。**
  **判定(`judge.ts`)はこの2つを区別しない。読む側が名乗りを確かめること。**

## 使い方

```console
# 起動条件だけ確認する(claude は起動しない)
$ mise exec -- bun run scripts/mcp-trial/run.ts --scenario bootstrap --dry-run

# 実行(証跡を残し、そのまま判定まで走る)
$ mise exec -- bun run scripts/mcp-trial/run.ts --scenario bootstrap

# 保存済みの証跡をあとから判定し直す
$ mise exec -- bun run scripts/mcp-trial/judge.ts docs/evidence/cp-6/transcripts/001-bootstrap
```

| フラグ | 既定値 | 意味 |
|---|---|---|
| `--scenario` | (必須) | シナリオID(`scenarios/<id>.md`)またはファイルパス |
| `--data-root` | **`data-<シナリオID>`** | 評価専用の `ST_DATA_ROOT`。既定はシナリオごとに分かれる(下記) |
| `--out` | `docs/evidence/cp-6/transcripts` | 試行ディレクトリを作る親 |
| `--note` | なし | 破棄した試行に付けるメモ |
| `--dry-run` | off | 引数だけ表示して終わる。**何も作らない**(下記) |

### データルートはシナリオごとに分かれる(既定。V1-M0-T06 (d))

既定の `ST_DATA_ROOT` は **`data-<シナリオID>`** である(`bootstrap` なら `data-bootstrap`)。
**明示指定しなくてもシナリオ間で衝突しない。**

v0 は既定が `data-cp6` 固定で全シナリオが同じデータルートを共有しており、005/T1 で
`create_app(app_id="book-log")` が前の試行 004 の成果物と衝突した。AI は確認せずに既存アプリの
流用へ方針転換し、**シナリオの前提が壊れて試行が破棄になった**(F-18。`docs/v0-bootstrap-log.md` §4-3)。
CP-7 の 001-t04-improvements が `--data-root` を明示指定して回避していたのは、
**既定が危ないことを人間が覚えていた**からであって、仕組みが守っていたからではない。

**共有したい場合は `--data-root` を明示する。** 例えば `out-of-vocabulary` は `bootstrap` が作った
アプリを対象にする前提なので、続けて回すなら両方に同じ値を渡す。

```console
$ mise exec -- bun run scripts/mcp-trial/run.ts --scenario bootstrap --data-root data-cp8
$ mise exec -- bun run scripts/mcp-trial/run.ts --scenario out-of-vocabulary --data-root data-cp8
```

**事故を既定にせず、共有を明示にした** —— これがこの変更の全部である。

### `--dry-run` は何も作らない(V1-M0-T06 (c))

`--dry-run` は**試行ディレクトリを作らず、連番も消費しない**。組み立てた `claude` の引数と
`ST_DATA_ROOT` を標準エラーに出して終わる。

v0 のハーネスは dry-run でも試行ディレクトリを作り、連番を1つ消費していた
(`docs/v0-bootstrap-log.md` §4-4)。**cp-6 の `001-bootstrap` がそれである** ——
`judge.json` も `meta.json` も無い空の試行が証跡に1件残り、
**外から見ると「7回試して1回失敗した」ように読める。**
証跡が1件多く見えることは検証記録の信頼性に直接効くので、直した。

### 試行ディレクトリの中身

```
<連番>-<シナリオID>/
├── meta.json     … シナリオ・セッションID・実引数・ターンごとの前後スナップショット
├── stream.jsonl  … stream-json の生ログ(複数ターンを1本に連結)
├── mcp.json      … この試行で使った評価専用の MCP 設定
└── judge.json    … 判定結果(機械抽出を含む)
```

**連番は破棄した試行も消費する。** 「何回試して何回捨てたか」がディレクトリ一覧だけで分かる。
捨てた試行は消さずに `--note` を付けて残すこと ―― CP-5 で最初の試行を捨てた事実は、
本文に書かれるまで証跡から復元できなかった。

## judge が「検証無効」を出す条件

| コード | 条件 |
|---|---|
| `unexplained_change` | **本命。** 観測されたファイル変化のうち、transcript 上の MCP ツール呼び出しで説明できないものがある |
| `change_between_turns` | ターンNの終了後、ターンN+1の開始前にデータが変化した(会話の外での改変) |
| `mtime_outside_run` | 変化したファイルの mtime が実行時間帯の外にある |
| `forbidden_tool_effective` | `system/init` の**実効**ツール一覧に、MCP ツールと `ToolSearch` 以外が含まれている |
| `expected_absent_tool_present` | 外したはずのツールが実効一覧に残っている(例: `broken-reference` の `get_manifest`) |
| `mcp_server_not_connected` | `smailtalk` の status が `connected` でない |
| `prompt_contains_code` | 人間ターンの本文にコードフェンス・JSON リテラル・波括弧入りのインラインコードがある |
| `evidence_missing` | 生ログに壊れた行がある / init 回数とターン数が合わない / 前後スナップショットが欠けている |

### なぜ「ツール使用回数0件」では足りないのか

transcript は「**AI が何をしたか**」の記録であって、「**人間が何をしなかったか**」の記録ではない。
ツールを1つも使っていなくても、別ターミナルで `sqlite3` を叩けばデータは変えられる。

そこで judge は逆向きに見る ―― **実際に起きた変化のほうを起点にして、
それを説明できる MCP ツール呼び出しが transcript にあるかを問う**。
`run.ts` は各ターンの前後で `ST_DATA_ROOT` 配下の全ファイルの SHA-256 と mtime を採取しており、
判定はこの2つの記録の突き合わせで行われる。

### 説明の強さは一様ではない(正直に書く)

- `manifest.json` と `snapshots/` は、スキーマを変えるツール(`create_app` / `apply_diff` / `undo`)でしか動かない。
  したがって「そのアプリへの成功した**書き込み**呼び出し」を要求できる ―― **強い説明**。
- `*.sqlite` / `-wal` / `-shm` は**参照系ツールでも動く**。SQLite は読むだけでファイルを作り WAL を書く。
  実測で `list_apps` を1回呼ぶだけで `kernel.sqlite` と `-wal` `-shm` の3つが生成される。
  ここで書き込み呼び出しを要求すると常に偽陽性になるので、「そのアプリ(またはカーネル)に触れた
  成功した呼び出し」まで緩めてある ―― **弱い説明**。judge は弱い説明しか付かない変化を警告に列挙する。

**この緩和は限界でもある。** SQLite の中身を人間が別経路で書き換えた場合、
参照系の呼び出しが1つでもあれば「説明が付いた」ことになってしまう。
バイト単位の変化だけでは、読んで動いたのか書いて動いたのかを区別できないためである。
**構造的な保証があるのはマニフェストとスナップショットの層だけ**である。

**強い説明が一段弱くなっていた件は、V1-M1-T08 で戻した。**
V1-M0-T01 で `update_record` / `delete_record` が `WRITE_TOOLS` に加わった結果、
**レコードしか触らない呼び出しまで `manifest.json` の変化の説明として列挙されていた**
(010-record-correction では `explainedBy` に `update_record` が5件並んでいた)。
`unexplained_change` の結論は変わらないが、**会話の外で `manifest.json` が書き換えられていても
同じアプリへの `update_record` が1件あれば「説明が付いた」ことになる**ので、
これは判定を**弱くする**向きの誤りだった。

現在は `attribution.ts` の **`MANIFEST_WRITE_TOOLS`**(`create_app` / `apply_diff` / `undo`)
だけがマニフェスト層の説明になる。**`WRITE_TOOLS` と同じく事実の列挙であって辞書ではない。**
分類の網羅は `attribution.test.ts` が検査する —— `MANIFEST_WRITE_TOOLS` と
`RECORD_WRITE_TOOLS` の和が `WRITE_TOOLS` と一致しなければ落ちるので、
**ツールが増えたら「マニフェストを書くのか」を決めるまで通らない**(沈黙による緩みを塞ぐ)。

**実測**(既存 transcript 全件): マニフェスト層の `explainedBy` の総数は
010 で 16→4、011 で 22→4、008 で 8→4 に絞られ、**説明不能になった変化は1件も無い**
(= 新しい `unexplained_change` を1件も生んでいない)。

**残る限界**: 絞ったのは**パスの種類ごと**であって、**どの差分がどのファイルを変えたか**では無い。
同じターンに `apply_diff` が複数あれば、そのすべてが同じ `manifest.json` の説明として並ぶ。
`weak` の判定(SQLite 層)は従来どおり `WRITE_TOOLS` 全体で見ており、そちらは緩いままである。

## CP-5 の弱点3つに対して、何を仕組みにし、何が残るか

### 弱点1: ファイル系ツールの隔離条件が口伝だった → **仕組みで解消**

CP-5 の最初の試行では、AI が `Grep` でリポジトリの `src/kernel/types.ts` を読み、
ツール説明文ではなく**ソースから語彙を学習していた**(cp-5.md §0-(a))。
ファイル系ツールを全面禁止して初めて検証が成立したが、その条件はどこにも固定されていなかった。

いまは3重に固定されている。

1. `buildClaudeArgs` が、`Bash` / `Read` / `Write` / `Edit` / `Grep` / `Glob` / `Task` /
   `WebFetch` / `WebSearch` のいずれかが `disallowedTools` に無ければ**例外を投げる**。
   条件を満たさない引数はそもそも組み立てられない。
2. 同じく `allowedTools` に `ToolSearch` が無ければ例外を投げる。これは緩和ではなく**証拠のため**である。
   AI が禁止ツールを試して `No matching deferred tools found` を受け取る様子が生ログに残ることで、
   「禁止が効いている」ことが観測できる(cp-5.md:20 と :34)。
3. judge が `system/init` の**実効**ツール一覧を検証する。設定したつもりではなく、効いた値を見る。

> **実測で分かったこと**: 疎通確認の初回で、`disallowedTools` に書いていない組み込みツール
> (`Task*` / `Cron*` / `SendMessage` / `EnterWorktree` / `Workflow` など17個)が実効一覧に残っており、
> judge が `forbidden_tool_effective` で弾いた。**設定値の検査だけでは見逃していた穴**である。
> シナリオ側の `disallowed_tools` は現行 CLI(2.1.214)の実測に合わせて埋めてあるが、
> **CLI が更新されて新しい組み込みツールが増えれば、また実効一覧に現れる。**
> そのときも judge が弾くので、シナリオの禁止リストに足して再実行すればよい。

### 弱点2: 狙ったエラー経路に到達できず未検証で終わった → **一部を仕組みで解消**

- **参照切れエラー**: CP-5 は4回試して毎回 AI が `get_manifest` で事前に気付き、到達しなかった。
  `broken-reference` シナリオは `get_manifest` を `allowedTools` から外し `disallowedTools` に入れる。
  judge が実効一覧に現れないことを検証するので、「外したつもり」で終わらない。
  ただし `list_records` / `list_apps` は許可したままなので、AI がそちらで不在に気付く逃げ道は残っている。

「何ターン目だったか」までである。**狙った経路に到達したかは人間が抽出結果を読んで判断する。**

### 弱点3: クライアントが Claude Code 1種類のみ → **今回も解消しない(限界として残る)**

### そのほか、判定できないこと

## 断りの抽出方式と、その失敗モード(V1-M0-T06 (a))

### なぜ変えたか

**旧方式は語尾の部分文字列一致だった**(「できません」「変えられません」「作れません」…)。
これは v0 で **最も深刻な事象を取りこぼした**(F-27):

| # | 出典 | 内容 | 落ちた理由 |
|---|---|---|---|
| 1 | 006/T2 | 「そのまま適用して」の明示指示に対し、ツールを1回も呼ばずに確認を差し戻した | **本文に判定語が1つも現れない** |
| 2 | 007/T3 | 自分が壊したレコードを「**私からは直せません**」と報告(F-37) | 「直せません」が辞書に無い |

**F-27 は「辞書に語を足す」を明示的に禁じている。** #2 は辞書に足せば拾えるが、
**#1 は本文に語が無いので何を足しても拾えない。** したがって方式そのものを変えた。

### 採用した方式: ターン単位の証跡照合

判定単位を「assistant テキスト1本」から**ターン**に上げ、独立した3つの入力を組にする。

1. **人間が何を頼んだか** —— `meta.json` の `turns`(judge が `detectRefusals` に渡す)
2. **AI が何を呼び、何が返ったか** —— そのターンのツール呼び出し数・書き込みの成否・エラー数
3. **AI が何と言ったか** —— 応答本文。ただし**語の一致だけでは断りと断定しない**

判定は2つの経路がある。**どちらも単独の語一致では成立しない。**

| 種別 | 成立条件 | 拾えるもの |
|---|---|---|
| `capability_denial` | **可能・能力の否定の語尾の形態**(語彙ではなく活用形。`せません` / `られません` / `えません` …)に一致し、**かつ**その文が限界の**帰属先**を名指ししている(`私` / `語彙` / `ツール` / `v0` …、**および実効ツール一覧に出てくる操作名**)か、同じターンで代替案が出ている | 007/T3 の「私からは**直せません**」。`せません` は活用形なので、**辞書に無い動詞でも拾える** |
| `action_withheld` | 人間が変更を頼んだのに、**書き込み系ツールが1件も成功しておらず**、ターンの最終応答に**問いの文が含まれる**(問いの判定は**文末の終助詞「か」または疑問符**という文法規則である。語尾の列挙ではない —— V1-M1-T08)。**AI の本文の語を一切見ない** | 006/T2 の差し戻し、010/T5 の削除前の同意取り(F-38) |

出力には必ず「**何に対する断りか**」が入る —— 人間の要求本文 / 断りの1文(切り詰めない) /
帰属先 / 判定に使った証跡(`evidence`)。旧方式の `matched` が1語だけで
「何を断ったのか分からない」状態だったことへの対処である。

**「書き込み系ツール」の中身は事実の列挙であって辞書ではない。**
`transcript.ts` の `WRITE_TOOLS` は `src/mcp/tools/write.ts` が登録するツールと一致していなければならず、
一致しなければ `action_withheld` は**実際に書いた AI を「行動を差し控えた」と誤検出する**。
実際 V1-M0-T01 が `update_record` / `delete_record` を足したとき、この定数は取り残されていた
(010-record-correction/T4 は `update_record` を5回成功させながら「書き込み成功0件」と記録されていた)。
**再発は `write-tools-drift.test.ts` が塞ぐ** —— `registerWriteTools()` だけを繋いだサーバの
`tools/list` と突き合わせるので、ツールが増えれば `WRITE_TOOLS` を直すまでテストが落ちる。

**帰属先の標識にツール名を使うのは、辞書ではなく証跡からの導出である** ——
`system/init` の実効ツール一覧に出てくる操作名(`update_view` / `undo` …)を scope に加えている。
AI は限界を操作の名前で言うことがあり(「`update_view` だけでは実現できません」)、
それは能力の帰属先として機械的に確かである。

**過剰に拾う(誤検出。CP-6 実測で3件)**

1. **自発的な限界開示を断りと区別できない**(006/T1)。AI は頼まれたことを全部やり遂げたうえで、

2. **帰属先も代替案も伴わない短い否定は落とす。** これは意図した設計である

4. **1ターンに複数の別々の断りがあっても1件に潰れる。** 台帳(§6-2)の単位が「試行/ターン」なので
   合わせた。**件数を「断りの個数」と読んではいけない。「断りが起きたターンの数」である。**

   **入力パース層のエラーはカーネルの `hint` も `allowed_values` も一切通っていない。**
   これを混ぜた自己修正率は、**カーネルのエラー設計が効いた証拠として読めない**。
   段階が出力に入ったので、**この読み替えは機械的にできる**(混ぜたまま論じる言い訳が無くなった)。
4. **F-17 / F-24 の再発件数は `stage: "input-parse"` の件数そのもので数える。**
   これが本節で作った唯一の新しい計数である。

### それでも残る限界(「塞いだ」ではない)

- **本タスクは F-17 を1件も減らさない。** 観測できるようにしただけである。
  **`\uXXXX` エスケープを防ぐ手段は `src/` にも `scripts/` にも無い**
  —— 入力がパースされるのは MCP クライアント側であり、カーネルでも MCP サーバでも捕捉できない。
  **構造的担保の検討は M4(V1-M4-T01)へ渡す。**
- **標本は2件だけである**(007/T1 と CP-5-20)。
- **クライアントは Claude Code 1種類である。** `__unparsedToolInput` は
  **Claude Code の stream-json 出力の形**であって、MCP プロトコルの仕様ではない。
  **別のクライアントでは残り方が違う可能性があり、その場合この判定は静かに 0件を返す**
  (`stage` が全部 `server` になる)。**0件を「再発しなかった」と読んではならない** ――
  まず `__unparsedToolInput` がそのクライアントに存在するかを確かめること。
- この事象が**モデル固有なのかクライアント固有なのかプロトコル固有なのかは切り分けられていない**。

## ツール呼び出し単位の時刻と、やり直しのコスト(V1-M0-T06 (b))

`stream.jsonl` の `assistant` / `user` イベントには `timestamp` が付いている。
`parseTranscript` はこれを `ToolCall.timestamp` / `ToolResult.timestamp` として拾い、
`detectRetries` が**やり直し1回あたりの所要時間**を算出する。

**「やり直し1回」の定義**: 直前の試行の**結果が返った瞬間** → 今回の試行の**結果が返る瞬間**。
この区間にモデルの再生成が丸ごと入るので、**やり直しが実際に消費した時間**がこれである。

```
docs/evidence/cp-7/transcripts/001-t04-improvements/ ターン1 apply_diff:
  3回試行 / 全体 19.4s / やり直し2回 / 1回あたり平均 9.7s(内訳 11.0s + 8.4s)
  うちツール実行そのものは 0.10s —— 残りはすべてモデルの再生成である
```

**時刻が無い証跡では、時間の項目を付けない。** `undefined` のまま返す ――
0 で埋めると「測って0だった」と「測っていない」が区別できなくなる(憲法6)。

## テスト

判定に関わるロジックはすべて純関数として切り出してあり、`claude` を起動せずにテストできる。
固定のサンプル transcript は `__fixtures__/*.jsonl` にある。

```console
$ mise exec -- bun test scripts/mcp-trial/
```

`run.ts` に残っているのはプロセスの起動とファイルの配置だけである
(引数の組み立ては `cli-args.ts`、状態採取は `snapshot.ts`、突き合わせは `attribution.ts` / `judge.ts`)。

### 保存済み `judge.json` の陳腐化を検出する(`evidence-drift.test.ts`。V1-M1-T08)

**証跡は判定器の版に紐づいている。** `judge.ts` / `transcript.ts` / `attribution.ts` を変えると
`docs/evidence/**/judge.json` は**黙って古くなる**。実際 V1-M0-T06 の方式変更以降、
CP-6 の6本がその状態で放置され、**`007/judge.json` の `refusals` が空配列のまま
「現在の判定」の顔をして置かれ続けていた**(F-27 が落とした状態のファイルである)。
撮り直しは行われたが、それは手で合わせただけで**再発は塞がれていなかった**。

`evidence-drift.test.ts` は、`meta.json` / `stream.jsonl` / `judge.json` が揃った試行を
全件洗い出し、**保存済みファイルと現行判定器の出力をバイト比較する**。
判定器の振る舞いが変われば、撮り直すまでテストが落ちる。

**版番号を `judge.json` に書き込む方式は採っていない。** 版番号は手で更新する定数であり、
**更新を忘れれば黙って通る** —— `WRITE_TOOLS` が取り残されたのと同じ失敗の形である。
出力そのものを突き合わせれば、宣言の有無に関係なく食い違いが出る。

**失敗モード(何を取りこぼすか)**:

1. **`judge.json` を持たない証跡は、この検査に一度も現れない。** CP-5 の7本がそれである
   (`meta.json` も `judge.json` も無く `stream.jsonl` だけ)。
   **陳腐化を検出できないのではなく、検査対象として存在しない。**
   `cp-6/001-bootstrap`(`--dry-run` の副産物)も同じ理由で対象外である。
2. **「一致していること」は「判定が正しいこと」を意味しない。** 判定器が壊れた状態で
   撮り直せば、壊れた出力どうしが一致して緑になる。
   このテストが保証するのは**保存済み証跡と現行判定器が同じものを言っていること**だけである。
3. **撮り直しの是非は判断しない。** 過去のチェックポイントの証跡を書き換えてよいかは
   人間の判断であり、テストは食い違いを知らせるところまでしかやらない。
