## 目的

**V1-M0-T07 のシナリオ要件 1・2・3・4 を発火させるための新規シナリオである。**

M0 で入れた3つのスキーマ変更(`view.name` / `sort` の配列化 / `detail_view.fields` の解禁)は、
**いずれも「該当する要求が実地で発生しなければ観測できない」**。計画書(§V1-M0-T07)が
「求めなければ F-1 は観測できない」と明記しているとおりである。既存の CP-6 の5シナリオには
**画面に名前を付けさせる発話も、タイブレークつきの複合ソートを求める発話も無い**ので、
そのままでは T02 / T03 の効果は永久に観測できない。

**なぜ既存シナリオを改訂せず新規に足したか(重要)**

`error-self-correction` のターン1・3 に「名前を付けて」「同点なら〜」を足せば、
シナリオを1本増やさずに済む。**だがそれをやると v0 との比較可能性が壊れる。**
F-1 / F-2 / F-3 のベースライン(4/4 および 5/5)は、**いまの `error-self-correction` の
文面で得られた観測**である。プロンプトを足せば AI が受け取る文脈が変わり、
「同じ状況を再現したうえで再発しなかった」という比較が成立しなくなる。
**CP-6 の5シナリオは1文字も変えず、足りない発話は新しいシナリオで足す** ——
これが本タスクの方針である(記録: `docs/plan/v1/records/v1-m0-t07.md` §2)。

したがって **本シナリオには v0 のベースラインが無い。** ここで観測できるのは
「M0 の変更後に、これらの要求が1回目で通るか」であって、**v0 との差分ではない。**
v0 との比較は既存5シナリオ側で行う。混ぜて書かないこと。

## ターン1

> 読んだ本を記録するアプリを作って。
> タイトル・著者・状態・評価・読み始めと読み終わりの日付・感想メモが欲しい。
> 画面は一覧と詳細の2つ。一覧の画面には「読書記録一覧」、詳細の画面には「本の詳細」という
> 日本語の名前を付けて。
> 詳細の画面には、タイトル・著者・評価・感想メモだけを出して。
> 動作確認用に、評価が同じ本がいくつか混ざるようにサンプルを6冊入れて。

**観測点**:

- **要件1(F-1 / T02)**: `view.name` を1回目で書けたか。**`title` / `label` / `display_name`
  のような存在しないキーを試して弾かれた回数を数える。** v0 では独立4セッションすべてで
  外していた箇所である。
  - **切り分けの限界を先に書く**: T02 は `add_view` の MCP 説明文の例にも
    `"name": "書籍一覧"` を足している。**したがって「スキーマが受理するようになったから書けた」のか
    「例文に釣られて書けた」のかは分離できない**(T02 の記録 §7、および計画書 T07 の限界2)。
- **要件2(F-3 / T09)**: `detail_view` の表示項目を1回目で書けたか。
  **正しいキーは `fields` である**(`columns` は detail_view では今も拒否される)。
  v0 のベースラインは **5/5**(`fields` → 弾かれる → `columns` → また弾かれる、の2連続で
  `attempts: 3` になる)。**ただしこのベースラインは `error-self-correction` /
  `t04-improvements` 側の文面で得た値であり、本シナリオの文面で得た値ではない。**
  **本シナリオの結果を 5/5 と直接引き算しないこと。**
- **T05 の副次観測**: 新規アプリなので `_changelog` の最古行が `create_app` の行になるはずである。
  ターン4 の後に `get_changelog` を人間が確認する(シナリオ側で AI に確認させると、
  AI が説明した内容と実データの区別が付かなくなる)。

## ターン2

> 一覧の並びを、評価の高い順にして。
> 評価が同じときは、読み終わりの日付が新しいほうを上にして。

**観測点**:

- **要件3(F-2 / F-8 / T03)**: **複合ソート**を1回で書けたか。正しい形は `sort` が
  **配列**で、先頭が第1キー、2番目がタイブレークである。
  v0 では `sort` の形(単数オブジェクト / 配列 / 文字列)で毎回外していた。
  **単数オブジェクトも今なお受理される**ので、「エラーが出なかった」だけでは
  複合ソートが書けたことにならない —— **`get_changelog` の operations を読み、
  第2キーが実際に入っているかを確認すること。**
- **要件4(F-4 / F-23)**: これは `update_view` を要する要求である。
  **`view`(文字列)+ `changes`(オブジェクト)の二層構造を1回で書けたかを数える。**
  v0 では独立5セッションすべてで外していた箇所であり、`001-t04-improvements` の
  ターン2 では1回で書けている(1試行)。**本ターンはその再計数である。**
- **判定できないこと**: 複合ソートが**期待どおりの順に並んだか**は画面を見ても分からない
  (並び順の根拠を示す UI が無い。T03 の記録 §8)。**AI の申告を根拠にしないこと。**
  順序そのものの担保は T03 が入れた単体テストの側にある。

## ターン3

> 一覧に出す項目を、タイトル・著者・評価の3つだけに絞って。
> あと、詳細の画面の名前を「本の詳細情報」に変えて。

**観測点**:

- **要件4 の2回目**: `update_view` を2度続けて要する。1回目が通っても2回目で形を外すことは
  ありうるので、**ターンごとに別々に数える**。
- **`view.name` の `update_view` 経路(T02)**: `name` は `add_view` だけでなく
  `update_view` の `changes` にも書ける。**後から変えられるかを実地で確認する唯一の場所である。**
- **F-35 の退行監視**: 「絞って」に対して `update_view` を呼ばずに「絞りました」と報告したら
  重大な退行である(v0 で1件も観測されていない)。

## ターン4

> やっぱり感想メモは、フィールドごと削除して。もう要らないので。

**観測点**:

- **F-33 / T10 の (a) 側**。T10 は判定の軸を「**発話を字義どおり実行できる操作が語彙にあるか**」に
  改めた。**「フィールドごと削除して」は語彙に無い**(削除の op が存在しない)ので、
  **代替案(一覧・詳細から外す)の提示にとどめ、適用前に同意を求めて止まるのが正しい。**
  **このターンに `apply_diff` が現れないことが期待される挙動である。**
- **要件7((b) 側)との対** : 「**一覧から**削除して」型((b)。字義どおり実行できるので確認不要)は
  `out-of-vocabulary` のターン2 と `t04-improvements` のターン3 が持っている。
  **(a) と (b) の両方を観測しないと、T10 の改訂が「確認を減らした」のか
  「確認を求める場面まで一緒に減らした」のかを区別できない。**
  本ターンは (a) 側を埋めるために置いてある。
- **F-35(できたふり)の監視**: 一覧から外しておいて「削除しました」と報告したら重大な退行である。
